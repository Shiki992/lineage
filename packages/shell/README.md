# @lineage/shell

The typed TypeScript side of the Lineage engine, the storage interface, and one method per panel button. Platform code (Word, later Google Docs) plugs in through two interfaces.

- `src/engine.ts`: `loadEngine(bytes)` (Node) and `loadEngineAsync(url)` (browser) return a typed `Engine`.
  - Engine failures throw `EngineError` with the panel's words.
  - A value that isn't the expected shape throws `EngineBoundaryError`.
  - After a Rust panic the engine reports itself crashed.
- `src/schemas.ts`: valibot schemas for everything that crosses the boundary (decision 0010). The golden replies in `test/golden/`, written by `crates/wasm/tests/golden.rs`, must all pass.
- `src/storage.ts`: the `Storage` interface, mirroring `crates/harness/src/storage.rs` (expected-version appends, blobs checked by SHA-256), plus `MemoryStorage`.
- `src/host.ts`: `DocumentHost`, the open document as bytes, ids and a few actions.
- `src/lineage.ts`: `Lineage`, the twin of `harness::Panel`:
  - fetches the blobs the engine asks for;
  - changes the document before appending to the ledger, reads every write back, and puts the original back if it didn't land;
  - on a conflicting append, undoes and runs again.
- `src/testing/`: the storage conformance suite every adapter runs, and `FakeHost`, a document host that behaves like Word.

TypeScript never parses document XML. Bytes go in, bytes come out.

`wasm-pkg/` is generated by `scripts/build-wasm.mjs` and is not committed; `pnpm test` and `pnpm typecheck` build it first.

```bash
pnpm --filter @lineage/shell test
```

- `lineage.test.ts`: the Phase 1 scenario end to end through the real wasm engine, plus conflicts, a write Word didn't take, unsaved files and history kept elsewhere.
- `schemas.test.ts`, `storage.test.ts`, `bridge.test.ts`, `spec.test.ts`: the boundary, storage, the byte bridge, and the public change-list schema.
